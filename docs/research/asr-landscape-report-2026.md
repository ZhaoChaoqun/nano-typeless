# 语音识别 (ASR) 前沿技术全景调研（2025/2026）

**聚焦：中文普通话 & 中英混合场景 · 面向开发者语音助手**

*为 `nano-typeless` 项目编写 — 2026 年 2 月*

## 1. 摘要：谁才是中文开发者场景下的"王者"？

**没有唯一的王者——最优选择取决于你的部署约束。**

| 约束条件 | 最佳选择 | 理由 |
|---|---|---|
| **最高精度（云端 API）** | **Seed-ASR / 豆包 ASR**（字节跳动） | AISHELL-1 CER 0.68%；比所有开源模型高 10-40%；内置语义顺滑 + ITN |
| **最高开源精度（离线）** | **Paraformer-Large**（FunASR 工具包） | AISHELL-1 CER 1.95%；加语言模型可达 1.68%；有流式变体 |
| **最佳速度/精度平衡（端侧）** | **SenseVoice-Small / Fun-ASR-Nano** | 10 秒音频仅需 70ms；内置 ITN + 标点；sherpa-onnx 开箱即用 |
| **最"智能"的输出（LLM 驱动）** | **Qwen3-ASR 1.7B** | LLM 解码器天然具备语义理解；支持流式；AISHELL-2 WER 2.71%；但端侧部署仍需 GPU |
| **nano-typeless 当前最优方案** | **保持现有双引擎架构** | SenseVoice Nano（默认）+ Fun-ASR-Nano（方言）；叠加轻量 LLM 后处理来修正技术术语 |

**核心洞察：** LLM 类模型（Qwen3-ASR、Seed-ASR）能输出更"聪明"的文本（自动格式化、去除口误与犹豫），但相对较重。传统模型（SenseVoice、Paraformer）快且易部署，但输出的文本"欠智能"，需要后处理。**面向开发者语音助手的最优架构 = 快速端侧 ASR + 轻量 LLM 后处理器。**

## 1.5 术语速查：读懂本报告的几个关键概念

> 如果你对 ASR 领域不太熟悉，建议先读完这一节，后面的表格和分析会更容易理解。

### 语义顺滑（Disfluency Removal）—— 去口误

我们日常说话时会有大量的犹豫、重复和填充词（"呃"、"那个"、"就是"），语义顺滑就是**自动去除这些口语杂质**，让转写文本读起来更像书面语。

| 用户实际说的 | 语义顺滑前（逐字转写） | 语义顺滑后 |
|---|---|---|
| 那个...我想...呃...部署一下那个pod | 那个我想呃部署一下那个pod | 我想部署一下那个pod |
| 就是就是我觉得这个方案不太行 | 就是就是我觉得这个方案不太行 | 我觉得这个方案不太行 |

目前只有 LLM 类模型（Seed-ASR 的 `enable_ddc` 参数、Qwen3-ASR 的 LLM Decoder）支持此功能。SenseVoice、Paraformer 等传统模型会**原封不动地输出所有内容**，包括"呃"和"那个"。

### ITN（Inverse Text Normalization）—— 反向文本规整，即数字/日期格式化

ASR 模型听到的是声音，默认会按**口语形式**输出文字。ITN 负责将这些口语化的数字、日期、单位等**转换成书面格式**，让输出更像人类打字的结果。

| ASR 原始输出（口语形式） | ITN 处理后（书面形式） |
|---|---|
| 幺九二点幺六八点零点幺 | 192.168.0.1 |
| 二零二六年二月二十七日 | 2026年2月27日 |
| 三百五十美元 | 350美元 |
| 百分之五十 | 50% |
| 幺三八零零零零幺二三四 | 13800001234 |

> **为什么叫"反向"？** 因为 TTS（文本转语音）做的是**正向**规整——把"192.168.0.1"读成"幺九二点幺六八点零点幺"。ITN 是这个过程的**逆操作**。

### 阿里的两个 ASR 团队 —— 为什么开发方标注不同

报告中你会看到两种阿里标注：**"阿里（Qwen 团队）"** 和 **"阿里（语音实验室）"**。它们是同一家公司、不同团队的产品：

| | Qwen 团队 | 语音实验室（原达摩院） |
|---|---|---|
| **代表产品** | Qwen3-ASR | SenseVoice、Paraformer、Fun-ASR-Nano |
| **技术路线** | LLM 驱动，模型较大（0.6B-7B） | 传统 ASR 架构，模型轻量（200M-800M） |
| **工具包** | 无独立工具包 | FunASR 工具包 |

近年两个团队有合并趋势，Qwen3-ASR 实际上结合了两边的技术。

### FunASR —— 容易混淆的名字

**FunASR 是阿里巴巴达摩院/通义实验室的开源 ASR 工具包**（类似于一个"模型商店 + 推理框架"），它本身**不是一个模型**。多个模型都"住"在 FunASR 这个工具包里：

| FunASR 工具包里的模型 | 用途 |
|---|---|
| **Paraformer-Large** | 离线高精度中文 ASR |
| **SenseVoice-Small** | 快速多任务 ASR（语音+情感+事件） |
| **Streaming Paraformer** | 流式中文 ASR |
| **CT-Transformer** | 标点恢复 |
| **FSMN-VAD** | 语音活动检测 |
| **Fun-ASR-Nano**（2025 年 12 月新发布） | SenseVoice 和 Paraformer 的后继模型 |

> 所以当你看到"Paraformer-Large（FunASR 工具包）"时，意思是"这个模型来自 FunASR 工具包"；而"Fun-ASR-Nano"是一个**具体的模型名称**，恰好名字和工具包很像，容易混淆。

### WeTextProcessing —— 不是模型，是一套规则引擎

报告中提到 Paraformer 的 ITN 依赖"外部（WeTextProcessing）"。**WeTextProcessing 不是一个 AI 模型，而是一个基于规则的文本处理工具包**，由 WeNet 团队（西北工业大学+出门问问）开源。

它的工作原理是用 **WFST（加权有限状态转换器）** 编写的规则来匹配和替换文本模式——本质上是一套大型正则表达式系统，但比正则更强大，能处理复杂的中文数字、日期、货币等嵌套模式。

**举例说明它的工作流程：**

```
输入："一百二十三点四五"

① Tagger（标注器）：识别出这是一个小数
   → decimal { integer: "123" fractional: "45" }

② Verbalizer（输出器）：按规则格式化
   → "123.45"
```

**WFST 是什么？**

WFST = **Weighted Finite State Transducer（加权有限状态转换器）**，用大白话说就是一种**"带分数的查找替换机器"**。

普通正则替换只能处理固定文本（`"一百"` → `"100"`），但中文数字有复杂的位值嵌套——"一百二十三"需要计算 1×100 + 2×10 + 3 = 123。WFST 就像一个流程图，从一个状态跳到另一个状态，逐步计算：

```
输入："一百二十三"

状态流转：
  一 → 识别为 1
  百 → 当前位=百，累计 1×100=100
  二 → 识别为 2
  十 → 当前位=十，累计 2×10=20
  三 → 识别为 3，位=个

输出：100 + 20 + 3 = "123"
```

"加权"是指遇到歧义时用权重选择最合理的路径：比如"一二三"可能是"123"也可能是"1、2、3"，权重帮助决策。

> 简单记忆：**WFST = 比正则更强大的规则引擎**，专门用来处理复杂的文本转换（如中文数字的位值系统）。

**与 AI 模型的对比：**

| | WeTextProcessing（规则） | SenseVoice 内置 ITN（模型） |
|---|---|---|
| 原理 | 人工编写的 WFST 规则 | 模型从训练数据中学习 |
| 速度 | <1ms | 0ms（随模型推理一起完成） |
| 准确性 | 覆盖到的模式 100% 准确 | 大部分准确，偶尔出错 |
| 灵活性 | 只能处理预定义模式 | 能处理训练数据中出现过的模式 |
| 可维护性 | 加新规则需手动编写 | 需要重新训练模型 |
| 技术术语 | 无法处理（如"M4芯片"） | 同样无法处理 |

**已内置的中文规则类别：** 基数词、日期、货币、分数、时间、度量衡、车牌号、IP 地址等 12 类。

> 简单理解：WeTextProcessing 就像一本"数字格式化字典"，模型不具备 ITN 能力时，就查这本字典来格式化输出。

### 其他常见术语

| 术语 | 含义 | 一句话解释 |
|---|---|---|
| **CER** | Character Error Rate（字错误率） | 衡量 ASR 精度的核心指标，越低越好。比如 CER 2% 表示每 100 个字错 2 个 |
| **WER** | Word Error Rate（词错误率） | 英文常用的精度指标，中文一般用 CER |
| **流式（Streaming）** | 边说边转写 | 音频一边输入，文字一边输出，不用等说完 |
| **离线（Offline）** | 说完再转写 | 需要等一整段话说完后，一次性输出结果 |
| **VAD** | Voice Activity Detection（语音活动检测） | 检测音频中"有人在说话"的片段，过滤静音 |
| **端侧（On-device）** | 在本地设备上运行 | 不依赖网络和云服务器，模型跑在你的电脑/手机上 |
| **热词（Hotword）** | 自定义高优先级词汇 | 告诉模型"这些词很可能出现"，提高特定术语的识别率 |
| **RTF** | Real-Time Factor（实时因子） | 处理 1 秒音频花多少秒。RTF=0.1 表示 1 秒音频只需 0.1 秒处理 |
| **AR** | Autoregressive（自回归） | 逐 token 串行生成，每个 token 依赖前面已生成的所有 token。代表：Qwen3-ASR、Whisper |
| **NAR** | Non-Autoregressive（非自回归） | 所有 token 一次性并行生成，速度快但缺乏前后依赖。代表：Paraformer、SenseVoice |
| **CTC** | Connectionist Temporal Classification（连接时序分类） | 一种 NAR 解码方式：Encoder 对每帧音频独立预测字符，然后合并重复并去除空白符，得到最终文本。SenseVoice 使用此方法 |
| **CIF** | Continuous Integrate-and-Fire（连续积分触发） | Paraformer 使用的长度预测机制：对 Encoder 输出逐帧累加权重，累加值超过阈值时"触发"一个 token 位置，从而预测输出序列长度，再一次性并行解码 |
| **GLM** | Glancing Language Model（扫视语言模型） | Paraformer 的训练技巧：训练时随机遮盖部分正确 token，迫使模型学会从不完整的上下文中预测，提升 NAR 解码质量 |
| **MoE** | Mixture of Experts（混合专家） | 模型内部有多个"专家"子网络，每次推理只激活其中少数几个，从而在保持大参数量的同时控制计算量。Seed-ASR 的 LLM 部分使用此架构 |

## 3. 深度分析："智能"输出与语义顺滑（去口误/犹豫）

### 问题场景

用户说：*"那个...我想...呃...部署一下那个 pod"*

| 模型 | 输出结果 | 行为分析 |
|---|---|---|
| **Qwen3-ASR** | "我想部署一下那个pod" | LLM Decoder 天然过滤填充词，输出语义化文本 |
| **Seed-ASR（豆包）** | "我想部署一下那个pod" | `enable_ddc=true` 启用"语义顺滑"后处理 |
| **SenseVoice** | "那个我想呃部署一下那个pod" | **逐字输出**，不做语义顺滑 |
| **Paraformer** | "那个我想呃部署一下那个pod" | **逐字输出**，不做语义顺滑 |

**结论：** LLM 类模型（Qwen3-ASR、Seed-ASR）能天然处理语义顺滑。传统模型需要额外后处理。对于 `nano-typeless`，可用轻量 LLM 后处理器（如 Qwen2.5-0.5B）来清理口误与犹豫词。

## 4. 深度分析：ITN（反向文本规整）

### 场景："幺九二点幺六八点幺点幺" → "192.168.1.1"

| 模型 | ITN 实现方式 | "幺九二" → ? | "M四芯片" → ? | 电话"幺三八" → ? |
|---|---|---|---|---|
| **Qwen3-ASR** | LLM 隐式 | "192"（大概率） | "M4芯片"（大概率） | "138"（大概率） |
| **SenseVoice** | 模型内置（`<ITN>` token） | "192"（基础规则） | "M4芯片"（大概率不行） | "138"（基础规则） |
| **Seed-ASR（豆包）** | API 参数（`enable_itn`） | "192" | 热词辅助 | "138" |
| **Paraformer** | 外部流水线（WeTextProcessing/WFST） | "192"（WFST 规则） | 热词辅助 | "138"（WFST 规则） |
| **Fun-ASR-Nano-2512** | 模型内置 | "192" | 热词辅助 | "138" |

### 各 ITN 方案详解

#### A. 模型内置 ITN（SenseVoice）

SenseVoice 在编码器输入前添加特殊 `<ITN>` token，模型从训练数据中学习 ITN 规则。可处理标准模式（数字、日期、货币），但**无法处理领域术语**（如"M4 chip"、"gRPC"）。

```swift
// nano-typeless 当前配置
config.model_config.sense_voice.use_itn = 1  // 启用模型内置 ITN
```

#### B. LLM 隐式 ITN（Qwen3-ASR、Seed-ASR）

LLM 骨干网络具有广泛的世界知识，因此能自然地格式化文本。"M四"会变成"M4"，因为 LLM 知道 Apple Silicon 的命名规则。这是最灵活的方案，但需要较大的模型。

#### C. 外部流水线 ITN（Paraformer + WeTextProcessing）

基于规则的 WFST 语法处理特定模式：

| 类别 | 输入示例 | 输出 |
|---|---|---|
| 基数词 | 一百二十三 | 123 |
| 电话号码 | 幺三八零零一二三四五六 | 13800123456 |
| 日期 | 二零二六年二月 | 2026年2月 |
| 货币 | 三百五十美元 | 350美元 |
| IP 地址 | 幺九二点幺六八 | 192.168 |

**局限：** 无法处理技术术语（Kubernetes、MySQL、gRPC）——需要热词列表或上下文偏置。

### 对 nano-typeless 的建议

**现状：** SenseVoice 的内置 ITN 可覆盖约 80% 的场景。剩余 20%（技术术语、复杂数字模式）可通过以下方案补充：

1. **方案 A（轻量级）：** 基于正则表达式的常见模式后处理
2. **方案 B（强力型）：** 小型 LLM 后处理（Qwen2.5-0.5B/1.5B）实现语义 ITN
3. **方案 C（均衡型）：** 热词列表 + WeTextProcessing WFST 规则

## 5. 深度分析：技术领域适配（"开发者模式"）

### 场景：用户说"我要用 Kubernetes 部署一个 gRPC 服务"

| 模型 | 期望输出 | 实际可能输出 | 技术术语准确率 |
|---|---|---|---|
| **Qwen3-ASR** | 我要用Kubernetes部署一个gRPC服务 | 我要用Kubernetes部署一个gRPC服务 | 高（LLM 知识加持） |
| **SenseVoice** | 我要用Kubernetes部署一个grpc服务 | 我要用酷伯乃特死部署一个... | 低（无技术领域训练） |
| **Seed-ASR** | 我要用Kubernetes部署一个gRPC服务 | 我要用Kubernetes部署一个gRPC服务（需热词） | 高（热词辅助） |
| **Paraformer** | 我要用Kubernetes部署一个GRPC服务 | 我要用（上下文模型辅助）部署一个GRPC服务 | 中（上下文模型） |

### 技术术语识别的解决方案

| 方案 | 适用模型 | 实施难度 | 准确率 |
|---|---|---|---|
| **热词列表** | Paraformer-contextual、Seed-ASR | 低（提供术语列表即可） | 对已知术语高 |
| **LLM 后校正** | 任意 ASR + 小型 LLM | 中（需构建流水线） | 对常见技术术语高 |
| **微调** | SenseVoice、Qwen2-Audio | 高（需标注数据） | 最高（领域定制） |
| **提示词工程** | Qwen3-ASR | 低 | 中高 |

### 可用的微调基础设施

## 6. 深度分析：流式延迟 vs. 精度

### MacBook 上的端侧流式架构选择

| 架构方案 | 延迟 | 精度 | 内存占用 | 复杂度 |
|---|---|---|---|---|
| **Streaming Paraformer**（sherpa-onnx） | 约 300-600ms 分块 | 良好（CER 约 2-3%） | 约 250MB | 低（原生流式） |
| **SenseVoice Nano + VAD**（sherpa-onnx） | 约 500ms-2s（VAD 分段） | 较好（CER 约 3%） | 约 200MB | 中（需调 VAD 参数） |
| **Qwen3-ASR 0.6B**（Rust FFI） | 约 2 秒分块 + token rollback | 最佳（LLM 智能输出） | 约 1.2GB | 中（已集成） |
| **nano-typeless 当前方案** | 约 500ms-2s | 良好 | 约 180MB + 57MB 运行时 | 低（已集成） |

### nano-typeless 当前架构（端侧最优设计）

```
音频输入 (16kHz 单声道)
    │
    ├─ [路径 1: SenseVoice Nano] ──→ VAD 分段 ──→ 离线转写 (70ms/10s) ──→ 内置 ITN + 标点
    ├─ [路径 2: Streaming Paraformer] ──→ 原生流式 (600ms 分块) ──→ 外部 CT-Transformer 标点
    └─ [路径 3: Qwen3-ASR 0.6B] ──→ 分块+回滚流式 ──→ 内置标点 (LLM)
          │
          ▼
    文本输入器（光标位置插入）
```

这已经是一个设计良好的架构。Qwen3-ASR 提供"智能"输出路径，而 SenseVoice/Paraformer 提供快速、稳定的路径。

## 8. 对 `nano-typeless` 的建议

### 问题一：是否应保留 Qwen3-ASR？

**是，保留它**，但作为引擎选项之一，而非唯一选择。Qwen3-ASR（0.6B）的优势：
- 内置标点（无需外部 CT-Transformer）
- 比传统模型更强的语义理解
- 通过分块+回滚实现合理的流式效果

不过，它比 SenseVoice/Paraformer 慢，且内存占用更大（约 1.2GB vs 约 179MB）。

**建议：** 保持当前三引擎架构。默认使用 SenseVoice Nano 追求速度，提供 Qwen3-ASR 给追求输出质量的用户。

### 问题二：SenseVoice 是否是更好的轻量替代？

**SenseVoice Nano 已经是项目默认引擎**，且表现良好。但建议在 sherpa-onnx 适配稳定后升级到 **Fun-ASR-Nano**：

| 升级路径 | 工作量 | 收益 |
|---|---|---|
| 保持 SenseVoice Nano（当前方案） | 零 | 快速、稳定、179MB |
| 新增 Fun-ASR-Nano 选项 | 低（sherpa-onnx 兼容） | 更高精度、方言支持、716MB |
| 用 Fun-ASR-Nano 替换 SenseVoice | 低 | 单模型最优精度 |

### 问题三：是否需要额外的 ITN 处理步骤？

**是的，面向开发者场景时需要。** 当前 SenseVoice ITN 可处理标准模式（数字、日期），但在以下场景表现不佳：
- 技术术语："Kubernetes"、"MySQL"、"gRPC" → 常被转写为乱码
- 混合格式："M4 chip"、"iPhone 16 Pro" → 格式不一致
- 代码片段："sudo rm rf"、"git push origin main" → 经常出错

**推荐方案（按实施难度排序）：**

#### 第一级：速赢方案（无需模型）
```
ASR 输出 → 正则/词典后处理 → 最终文本
```
- 维护一个技术术语词典（500-1000 个词条）
- 编写正则规则处理常见模式（IP 地址、版本号）
- 完全在 Swift 中实现，零延迟开销

#### 第二级：智能后处理（小型 LLM）
```
ASR 输出 → Qwen2.5-0.5B/1.5B 校正 → 最终文本
```
- 用量化的 0.5B LLM "清洗" ASR 输出
- 同时处理语义顺滑 + 技术术语校正 + 格式化
- 额外约 100-300ms 延迟；额外约 500MB 模型大小
- 可通过 CoreML 在 Apple Neural Engine 上运行

#### 第三级：完整"开发者模式"（微调）
```
在开发者领域数据上微调 SenseVoice / Fun-ASR-Nano
```
- 收集 100-1000 小时开发者语音数据
- 用技术词汇微调 SenseVoice 或 Fun-ASR-Nano
- 精度最高，但需大量数据采集工作

### 架构建议

```
┌─────────────────────────────────┐
│       nano-typeless v2.0        │
│                                 │
│  ┌──────────┐  ┌──────────────┐ │
│  │ 极速路径 │  │  智能路径    │ │
│  │ SenseVoice│  │ Qwen3-ASR   │ │
```
